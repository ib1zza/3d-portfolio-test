# 03 — Движение: скролл, хореография, переходы

## 1. Скролл как единственный источник времени

Весь сайт — одна партитура. Ни одна анимация не запускается «по таймеру»: всё
привязано либо к прогрессу скролла, либо к явному действию пользователя. Это даёт
две вещи: полную обратимость (проскроллил назад — всё вернулось) и предсказуемость
на любой скорости прокрутки.

### 1.1 Lenis

```ts
// src/motion/smooth-scroll.ts
const lenis = new Lenis({
  autoRaf: false,          // цикл отдаём R3F
  duration: 1.1,
  easing: (t) => 1 - Math.pow(1 - t, 3),
  syncTouch: true,         // на мобилке тоже свой скролл
  syncTouchLerp: 0.09,
  touchInertiaExponent: 1.7,
  gestureOrientation: 'vertical',
})
addEffect((time) => lenis.raf(time))
```

Отключаем Lenis полностью, когда:
- `prefers-reduced-motion: reduce`;
- тир качества `flat`;
- открыто модальное окно или мобильное меню (иначе фон скроллится под ним);
- фокус находится в поле ввода на iOS (иначе едет вьюпорт).

`syncTouch: true` — сознательный риск: на слабых Android он может ощущаться
«ватным». Поэтому на тирах `medium`/`flat` включаем нативный тач-скролл, оставляя
Lenis только на десктопе. Проверять на реальном устройстве, а не в эмуляторе.

### 1.2 Стор скролла

Один слушатель Lenis пишет в zustand, все остальные читают:

```ts
lenis.on('scroll', ({ scroll, limit, velocity, direction }) => {
  const s = useScrollStore.getState()
  s.progress = scroll / limit
  s.velocity = clamp(velocity / 40, -1, 1)   // нормализуем
  s.direction = direction
})
```

Скорость дополнительно сглаживается в кадре, чтобы шейдеры не дёргались:

```ts
useFrame((_, dt) => {
  smoothVelocity = damp(smoothVelocity, useScrollStore.getState().velocity, 6, dt)
  uniforms.uVelocity.value = smoothVelocity
})
```

### 1.3 Прогресс внутри секции

Хук, который отдаёт `0..1` для диапазона документа. Основа всей хореографии:

```ts
export function useScrollRange(ref: RefObject<HTMLElement>, offset = ['start end', 'end start']) {
  // ResizeObserver + IntersectionObserver для границ,
  // пересчёт границ только при resize, не каждый кадр
  // возвращает { get(): number } — читается императивно в useFrame
}
```

Секции регистрируются в общем реестре, чтобы HUD знал название активной секции,
а система префетча — какая сцена следующая.

## 2. Хореография камеры

Камера одна на весь сайт. Она не «прыгает» между сценами — она едет по заранее
описанному пути, где ключевые кадры привязаны к прогрессу скролла.

```ts
// src/webgl/rig/camera-path.ts
export const CAMERA_KEYFRAMES: Keyframe[] = [
  { at: 0.00, pos: [0, 0, 9],    look: [0, 0, 0],    fov: 38 },  // hero
  { at: 0.12, pos: [1.6, 0.4, 6], look: [0, 0, 0],   fov: 34 },  // манифест
  { at: 0.28, pos: [0, -0.6, 5],  look: [0, -0.4, 0], fov: 40 }, // фокус
  { at: 0.45, pos: [0, 0, 2.5],   look: [0, 0, -12],  fov: 55 }, // коридор опыта
  { at: 0.62, pos: [0, 0.8, 6],   look: [0, 0, 0],    fov: 36 }, // скиллы
  { at: 0.82, pos: [0, 0, 8],     look: [0, 0, 0],    fov: 32 }, // витрина
  { at: 1.00, pos: [0, 0, 5.5],   look: [0, 0, 0],    fov: 40 }, // контакты
]
```

Реализация: интерполяция по `CatmullRomCurve3` для позиции, отдельная кривая для
точки взгляда, плюс `damp` поверх — так камера догоняет цель мягко, а на резком
скролле возникает естественное «запаздывание», которое читается как вес.

Поверх пути — три модификатора:
- **Parallax от указателя** (десктоп): смещение до ±0.25 юнита, `damp` 0.08.
- **Гироскоп** (мобилка, если пользователь дал разрешение): ±0.15 юнита.
- **Shake от скорости**: при velocity > 0.6 добавляется микродрожание с шумом,
  амплитуда 0.01. Даёт ощущение разгона.

На мобилке FOV увеличивается на 8–12 градусов и объекты отодвигаются: иначе в
вертикальном вьюпорте всё обрезается.

## 3. Переходы между страницами

Самая сложная и самая ценная часть. Задача: переход `/` → `/work/simplex` должен
выглядеть как **влёт внутрь портала**, а не как смена страницы.

### 3.1 Разделение ответственности

| Слой | Механизм | Что делает |
| --- | --- | --- |
| DOM | React 19 `<ViewTransition>` + Next 16 `experimental.viewTransition` | Кроссфейд и сдвиг текстовых блоков, shared element для заголовка проекта |
| WebGL | Собственный оркестратор на FBO | Раскрытие портала, перелёт камеры, морфинг частиц |
| Синхронизация | `transition-store` | Обе стороны читают один и тот же `progress` |

Критически важная деталь: **canvas нужно исключить из снапшота View Transitions**.
Браузер при `startViewTransition` делает растровый снимок старого DOM, и живой
WebGL-canvas в этом снимке превращается в застывший кадр — получится заметный
«стоп-кадр» посреди перехода.

```css
canvas.webgl-root {
  view-transition-name: none;
  /* и держим сам canvas вне поддерева, которое анимируется */
}
```

Настройка Next: **никакой настройки не нужно.** Проверено на установленном
Next 16.3.4: флаг `experimental.viewTransition` из типов конфига удалён, а Next
бандлит React canary `19.3.0`, где `ViewTransition` и `addTransitionType`
экспортируются напрямую. `transitionTypes` на `<Link>` тоже доступен без флагов.

Единственная тонкость: установленный в проекте `react` — стабильный `19.2.8`,
и его типы (`@types/react`) про `ViewTransition` не знают. В App Router `react`
резолвится в бандлёный canary, поэтому рантайм работает, а типы нужно объявить
самим:

```ts
// src/types/react-view-transition.d.ts
declare module "react" {
  export const ViewTransition: React.ComponentType<{
    name?: string;
    default?: "auto" | "none";
    children?: React.ReactNode;
  }>;
  export function addTransitionType(type: string): void;
}
```

```tsx
// app/work/[id]/page.tsx  — ViewTransition ставим на уровне страницы, не layout
import { ViewTransition } from 'react'

export default function Page({ params }) {
  return (
    <ViewTransition default="none" name={`project-${params.id}`}>
      <ProjectPage ... />
    </ViewTransition>
  )
}
```

`default="none"` обязателен: иначе каждая навигация будет запускать анимации во
всех обёрнутых компонентах и конкурировать с нашим WebGL-переходом.

Направление перехода передаём через `transitionTypes` на `<Link>`
(доступно с Next 16.2) и разбираем в CSS через `:active-view-transition-type(...)`.

### 3.2 Сценарий «влёт в портал»

```
[0.00] Клик по карточке проекта.
       Запоминаем: мировые координаты и размер портала, id проекта, акцентный цвет.
[0.00] router.push внутри startTransition + addTransitionType('portal-enter').
       transition-store.phase = 'leaving'.
[0.00–0.35] WebGL: камера летит к плоскости портала, портал раскрывается
       (радиус маски идёт от размера карточки к полному экрану),
       акцентный цвет вливается в свет и bloom.
       DOM: старый контент уходит вверх и растворяется через ViewTransition.
[0.25] Новая страница уже смонтирована (RSC отдал текст мгновенно),
       но её DOM-слой имеет opacity 0.
[0.35–0.60] Портал схлопывается в новый мир: камера уже внутри,
       частицы морфят из общего облака в модель проекта.
[0.60–0.85] DOM нового кейса проявляется снизу вверх, блоками, с задержкой 40мс
       между блоками. Заголовок проекта — shared element, он «прилетел» из карточки.
[0.85–1.00] Постпроцессинг возвращается в норму, phase = 'idle'.
```

Общая длительность: 900 мс на десктопе, 650 мс на мобилке. Дольше — раздражает
при повторных заходах, поэтому со второго перехода в сессии длительность
сокращается на 30% (`sessionStorage`).

### 3.3 Запасной механизм: FBO-кроссфейд

Для переходов, где нет портала (`/` → `/playground`, `/work` → `/resume`), делаем
чисто шейдерный переход: старая сцена рендерится в `renderTarget A`, новая — в
`renderTarget B`, полноэкранный квад смешивает их по шуму с направленным
смещением UV.

```glsl
float n = fbm(vUv * 3.0 + uTime * 0.1);
float m = smoothstep(uProgress - 0.15, uProgress + 0.15, n);
vec2 offset = vec2(0.0, (1.0 - m) * 0.06 * uProgress);
vec3 col = mix(texture2D(uFrom, vUv + offset).rgb,
               texture2D(uTo,   vUv - offset).rgb, m);
```

Стоимость — два прохода на время перехода. Это допустимо, потому что переход
короткий и в этот момент остальные системы (физика, GPGPU) ставятся на паузу.

### 3.4 Навигация назад

Кнопка «назад» браузера — самая частая точка отказа таких сайтов. Требования:
- `popstate` тоже запускает WebGL-переход, но в обратную сторону;
- позиция скролла восстанавливается **после** окончания перехода, иначе видно рывок;
- если пользователь нажал «назад» во время перехода — текущий прерывается,
  новый стартует с текущего `progress`, без ожидания.

## 4. Микровзаимодействия

### 4.1 Указатель

Не «кастомный курсор-кружок» (это уже банально), а **3D-объект в сцене**:
маленькая линза из `MeshTransmissionMaterial`, которая летит за курсором с
задержкой, слегка искажает то, что под ней, и тянет за собой точечный источник
света. При наведении на интерактивный элемент линза расплющивается в кольцо и
подсвечивает элемент светом акцентного цвета.

Обязательно: нативный курсор **не скрываем** над текстом и полями ввода. Скрываем
только над зонами с явным 3D-взаимодействием.

На тач-устройствах вместо линзы — «капля» в точке касания, живущая 400 мс.

### 4.2 Магнитные элементы

Кнопки и ссылки притягивают линзу и слегка смещаются сами (максимум 6 px, `damp`).
Реализация — общий хук `useMagnetic(ref, strength)`, работает на DOM-элементах,
координаты уходят в WebGL для подсветки.

### 4.3 Реакция текста на скорость

```ts
// wght: 700 в покое → 380 на максимальной скорости
const wght = 700 - Math.abs(smoothVelocity) * 320
el.style.fontVariationSettings = `'wght' ${wght}, 'wdth' ${100 + velocity * 8}`
```

Применяем только к дисплейным заголовкам, только на десктопе и только когда
`prefers-reduced-motion` не установлен. Обновление — через `will-change` и не
чаще раза в кадр.

### 4.4 Появление контента

Стандартный reveal — не «fade in up» на 30 px, а расслоение: блок появляется как
три копии с разным смещением и разным цветовым каналом, которые за 350 мс
сходятся в одну. Микро-хроматическая аберрация на уровне DOM, рифмуется с
WebGL-эффектом. Реализуется через CSS `text-shadow` и `mix-blend-mode`, стоит
почти ничего.

## 5. Горизонтальные секции

Две секции скроллятся горизонтально: коридор опыта и витрина проектов на десктопе.

Правила, чтобы это не бесило:
- Вертикальный скролл конвертируется в горизонтальный только пока секция занимает
  весь экран, и с чётким «выходом»: доехал до конца — страница продолжает ехать вниз.
- Индикатор прогресса секции виден всегда.
- Работают стрелки, `Home`/`End`, свайп, drag мышью.
- На мобилке горизонтальный скролл — нативный snap-контейнер, без хайджека.

## 6. Уважение к настройкам пользователя

При `prefers-reduced-motion: reduce`:
- Lenis выключен, скролл нативный;
- камера не летает, каждая секция имеет фиксированную позицию камеры, смена — мгновенная;
- частицы статичны, но видны (объект собран, а не в процессе сборки);
- переходы страниц — простой кроссфейд 150 мс;
- variable-font анимации выключены.

Важно: reduced motion **не должен** приводить к пустому сайту. Пользователь должен
увидеть все те же объекты, просто без движения.
