# 05. Архитектура и качество исполнения

## Базовое решение

Сохранить Next.js, React, R3F, Three и существующий общий Canvas. Для этой задачи смена framework или миграция на WebGPU не даёт необходимого визуального результата сама по себе. Зависимости зафиксировать через существующий lockfile; новые пакеты добавлять под доказанную потребность.

Перед любым изменением кода следовать `AGENTS.md`: прочитать нужные руководства в `node_modules/next/dist/docs/`. Сейчас каталог зависимостей отсутствует, поэтому конкретные новые Next API здесь не предписываются. После установки проверить актуальные правила server/client boundaries, lazy loading, images/fonts, navigation и caching.

## Разделение ответственности

| Слой | Ответственность |
| --- | --- |
| Server DOM | Весь существенный текст, ссылки, медиа и метаданные; сайт доступен без Canvas |
| Scene manifest | Ассеты, профили композиции, poster, диапазоны камеры, параметры материала |
| Scene director | Активный эпизод, локальный progress, жизненный цикл, переходы |
| Render layer | Единственный Canvas, освещение, ресурсы, качество и postFX |
| Motion policy | Настройки reduced motion, touch, видимость вкладки и допустимые анимации |
| Interaction bridge | Связь DOM focus/hover/selection со сценой; 3D не владеет навигацией |

Предлагаемые модули при реализации: `src/webgl/director/`, `src/webgl/scenes/tension/`, `src/webgl/materials/`, `src/content/scene-manifest.ts`. Это будущая структура; файлы пока не создаются.

## Scene director и scroll

У каждой сцены состояния `idle → preloading → ready → active → retiring → disposed`, а также `error`. В `ready` готовность означает загруженные необходимые ассеты и пригодный первый кадр; один процент загрузки файлов этого не гарантирует.

В обычном состоянии активна одна тяжёлая сцена. Следующая может быть загружена без постоянного рендера. Во время перехода допускается кратковременное перекрытие двух сцен, если оно укладывается в бюджет. После выхода остановить callbacks, снять интерактивность и освободить ресурсы, которыми сцена владеет единолично. Общие geometry/material/texture клоны требуют учёта совместного владения.

Прогресс вычислять из фактических границ секции; измерения обновлять после загрузки шрифта, resize и изменения контента. Не опираться только на процент всей страницы. Направление и скорость — дополнительные сигналы с clamp, а не источник основного состояния.

Для DOM и WebGL — один согласованный источник прогресса. В frame callbacks не создавать объекты и не вызывать React setState на каждый кадр. При переходе к demand rendering отдельно обеспечить работу Lenis и инвалидирование кадров: текущая зависимость SmoothScroll от R3F требует осознанной переработки, а не механического `frameloop="demand"`.

## Загрузка и отказоустойчивость

Первым загружается DOM с poster. Затем движок и hero-ассеты. Следующие сцены — по близости к viewport или намерению открыть кейс, с учётом save-data. Не preload всех GLB, видео и texture заранее.

Шейдеры нужной сцены прогревать вне заметного перехода, если установленная версия и текущий стек позволяют. `compileAsync` — предусмотренный Three.js механизм асинхронной компиляции; его интеграцию проверить на сцене, а не считать гарантией отсутствия всех GPU-стопов. [WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html).

При сетевой ошибке или невозможности WebGL остаётся poster и весь контент. При context loss остановить тяжёлую работу, показать стабильное изображение, дать доступную попытку восстановления. Элемент статуса должен находиться вне скрытого от accessibility дерева. Не удерживать пользователя на бесконечном loader. Зафиксировать резервный переход к poster, если готовность затянулась более чем на 4 секунды; фоновая загрузка может продолжиться.

## Качество и движение — независимые оси

| Режим | Изображение | Движение |
| --- | --- | --- |
| High | Полные материалы, LOD0, выбранный AA, локальный bloom при необходимости | Весь сценарий |
| Medium | LOD1, DPR 1–1.25, статическое окружение, простые тени, без дорогих screen effects | Тот же смысл, меньше вторичных колебаний |
| Reduced motion | High/medium по мощности либо poster по выбору | Без полёта камеры, parallax, волн и scroll-деформации |
| Static / save-data / WebGL unavailable | Качественные отдельные poster | Нативные переходы и scroll |

Не выбирать максимум автоматически только по названию GPU. Эвристика — старт; решение подтверждается sustained frame time в видимой вкладке после прогрева. Понижение сначала снижает DPR и дополнительные проходы, затем детализацию. Hysteresis и cooldown предотвращают переключения туда-сюда. В интерфейсе оставить понятный выбор «Полная графика / Лёгкая / Статичная» без показа инженерного жаргона.

## Исходные бюджеты

Это критерии данного проекта для первого фрагмента. При изменении бюджета записать причину и сравнение кадров; не выдавать цель за уже достигнутый замер.

| Метрика | Цель | Как проверять |
| --- | --- | --- |
| LCP | ≤2.5 s | Реальный DOM/poster, mobile lab до релиза и p75 field после |
| INP | ≤200 ms | Реальные открытия меню, кейса, контакт; field после релиза |
| CLS | ≤0.1 | Загрузка шрифтов, poster → Canvas, смена языка |
| Desktop animation | Около 60 fps, p95 frame interval ≤20 ms | 30 s записи после прогрева |
| Mobile medium | Устойчивые ≥30 fps, p95 interval ≤36 ms | Реальное устройство, повтор после 3 min нагрева |
| First-view transfer | ≤2 MiB DOM + styles + fonts + poster до WebGL | Cold cache network log |
| Отложенный hero-пакет | ≤3 MiB дополнительно, включая требуемый runtime и ассеты | Отдельный суммарный network budget |
| Геометрия активного кадра | ≤180k triangles high; ≤70k medium | Renderer counters с учётом всех объектов |
| Draw calls | ≤100 high; ≤60 medium до отдельных postFX passes | Renderer counters и число проходов |
| Текстуры + render targets | Ориентир ≤128 MiB high; ≤64 MiB medium | Расчёт форматов, размеров, mipmaps; это не полный измеритель GPU memory |

Пороги Core Web Vitals соответствуют [web.dev](https://web.dev/articles/vitals). Остальные числа — инженерные гипотезы проекта. Lab-тест не подтверждает field INP, а Lighthouse score не заменяет GPU-профилирование.

Отдельно контролировать пиковую память перехода. Двойной render target высокого DPR может стоить больше, чем сами GLB. Memory leak искать повтором 10 переходов и проверкой, что количество ресурсов возвращается к ожидаемому уровню.

## Доступность и mobile

- Все действия доступны через DOM keyboard/touch, с видимым focus и логичным порядком.
- Обычный текст: целевой контраст 4.5:1, крупный 3:1; фактические пары сверить в реализации. Touch target проектировать не меньше 44×44 CSS px как внутренний критерий.
- Canvas декоративный, существенные сведения не спрятаны в texture. Для poster не дублировать длинным alt тот же текст, который уже дан рядом.
- Без обязательного drag, hover, звука, горизонтального перехвата scroll или удержания клавиши.
- Проверить 200% zoom, увеличенный системный текст, 320 px ширину, landscape, safe areas и мобильную адресную строку.
- При reduced motion выключать все соответствующие callbacks, а не только CSS transition.
- Для читателя с клавиатурой нет многоэкранной ловушки pinned-section: ссылки и содержимое идут в естественном порядке.

## Проверки реализации

Автоматизировать важные сценарии: открытие главной/кейса напрямую, переход и Back, язык, контакт, static fallback, reduced motion, сетевой отказ ассета. Визуальные контрольные кадры фиксировать в выбранных progress с deterministic seed/time.

Браузеры: Chromium, Firefox, Safari desktop; Safari на реальном iPhone и Chrome на реальном Android. До этапа B выбрать и записать точные устройства, ОС и версии. Минимальные категории: ноутбук со встроенной графикой, iPhone нескольких поколений давности, Android среднего класса. Desktop emulation не заменяет тепловой и GPU-тест телефона.

Существующие `lint`, `typecheck`, `build` запускать на каждом законченном изменении реализации. В этой итерации изменяются только Markdown-планы, поэтому сборка не выполняется.
